KVCache 布局

对齐原理与计算口径
  1. 先分清 TP 与 DCP。 KDA 的 96 个头按 TP8 切成每卡 12 个。Attention KV、Indexer K 和 draft MLA 按 DCP 分 token，本地 1536 token 的物理页在 DCP8 下对应 12288 token 的逻辑覆盖，在无 DCP 的对照场景下覆盖 1536 token。
  2. 再对齐物理页。 历史部署的 CLI block size 为 768，启动日志中的有效本地 block size 是 1536。按 DSpark3 每层 KDA 原始状态为 841,728 B，主 MLA 页为 1536 × 656 = 1,007,616 B。KDA 状态对齐到主 MLA 页后，同一个物理槽可以按 ID 归属由两种缓存分别使用。Indexer 和 draft 分配各自的页宽。
  3. 最后按池 ID 结算。 这里按输入、生成预算和投机预留取整到整逻辑 block。KDA 有三组，每组持有两份基础状态页的规划上界。关闭 RecoverSSM 时，每组再加 numspec 份。每个状态 ID 依然占用整个物理池 ID 的 backing。

模型按独享请求、无前缀复用计算。投机预留用于计算页数。max_model_len 列仍是输入与可生成预算之和。全池 null ID、模型权重、图内存和按引擎槽数分配的 RecoverSSM records 独立于该请求的 block 计费。

本页固定采用 A5 Atlas 的 1536-token 页几何。改变开关时重算页数、状态及池分项。实际启动时如发生重新定页，应当用对应部署的 cache spec 校准。两份基础状态页采用容量规划上界。
